     1→# TA Workbench — Forex & Binary Options Technical Analysis Platform
     2→
     3→A user-defined technical-analysis platform: **you** create, organize, version and
     4→evaluate your own trading strategies. The platform is *not* a signal generator,
     5→has no built-in mandatory indicators or trading rules, executes **no orders**,
     6→and **never fabricates market data**.
     7→
     8→**Phase 3 (this repository)** builds the **Custom Strategy Builder** on top of
     9→the Phase 1/2 foundation (FastAPI + PostgreSQL, MetaTrader 5 market-data
    10→integration, Next.js/TypeScript frontend, Docker Compose, full test suites):
    11→
    12→* user-managed **categories, subcategories, strategies** with ownership
    13→  scoping (`X-User-Id` header, default `local`);
    14→* a **draft → validate → publish** workflow with **immutable, versioned**
    15→  rule sets (published definitions are frozen; historical analyses stay
    16→  stable; superseded versions remain readable forever);
    17→* a **versioned rule-set schema 2.0** — parametric conditions, optional
    18→  rules, rule ordering, symbol scope, market-regime applicability, evaluation
    19→  settings, direction `both` — documented in
    20→  [`docs/strategy-rule-schema.md`](docs/strategy-rule-schema.md) with a
    21→  generated JSON Schema;
    22→* a **rule-type registry** (`GET /api/v1/rule-types`): eight operational
    23→  rule types (price vs level, candle properties, candlestick patterns,
    24→  swing highs/lows, HH/HL/LH/LL structure, generic market-structure breaks,
    25→  moving averages, price zones) plus *planned* types (MSS/CHoCH, liquidity
    26→  sweeps, FVG, order blocks, breaker blocks, S/R reactions) that are
    27→  clearly marked NOT operational and rejected by validation;
    28→* a professional, responsive **Strategy Builder UI** (visual rule tree,
    29→  registry-driven parameter forms, inline validation errors, publish
    30→  preview, duplication, archiving, unsaved-changes guard) with an advanced
    31→  JSON editor for power users.
    32→
    33→Automatic order execution and profitability claims remain **out of scope
    34→forever**; strategy analysis on LIVE candles is the next phase.

    38→## Product principles
    39→
    40→| Principle | Implementation |
    41→|---|---|
    42→| User-defined strategies | Users build their own categories, strategies, conditions, AND/OR groups, confirmation & invalidation rules. Nothing is imposed. |
    43→| Explainable analysis | Every evaluation returns a per-condition tree: met / missing, numeric evidence, criteria and data-quality warnings. |
    44→| Explicit whitelist | Condition types, operators, fields, group logic, modes and timeframes are enumerated server-side (`/api/v1/meta`); anything else is rejected with precise error paths. |
    45→| Versioned rule sets | Saving a rule set creates a NEW immutable **draft** version (`strategy_versions.status`); publishing freezes a definition and supersedes the previous one. History is never rewritten — ready for later backtesting. |
    46→| Ownership | Every category/strategy is scoped to an owner (`X-User-Id` header; default `local`). Foreign-owned records are indistinguishable from missing ones (404 — no existence leak). |
    47→| No arbitrary code execution | Rule sets are pure data interpreted by a deterministic evaluator. No `eval`, no user expressions. |
    48→| Forex / Binary Options separation | Separate modes everywhere: API filtering, rule validation and default timeframe profiles (Forex: D1, H4, H1, M15, M5, M1). Binary Options strategies **default to M1**; higher timeframes are used only when the user explicitly declares them — never forced. |
    49→| Honest market data | If MetaTrader 5 is not connected the API and UI say so plainly and serve NOTHING. Every candle payload carries `data_provenance` (`mt5_live` / `postgres_cache`), `data_status` and data-quality warnings (gaps, duplicates, invalid OHLC, staleness). Forming candles are flagged and can be excluded with `closed_only=true`. |
    50→| No fabricated prices | The MT5 adapter is the only data source; missing history is reported, never back-filled, interpolated or synthesized. |

    80→### MT5 integration topology (important)
    81→
    82→The `MetaTrader5` Python package only runs where the terminal runs.
    83→
    84→- **Recommended**: run the backend **natively on the Windows host** with the
    85→  MT5 terminal installed, running and logged in. `pip install -r
    86→  requirements-mt5.txt`, set `DATABASE_URL` (plus optional `MT5_*` settings),
    87→  start uvicorn. The backend attaches to the terminal via its IPC bridge.
    88→- **Wine**: possible with Windows Python under Wine, unsupported here — test
    89→  carefully before relying on it.
    90→- **Docker Compose (Linux containers)**: MT5 **cannot** run inside the
    91→  container. Compose therefore starts the backend with `MT5_ENABLED=false`
    92→  (safe disabled mode — API and UI report it honestly). PostgreSQL and the
    93→  rest of the platform keep working; alternatively point the frontend at a
    94→  backend running on a Windows machine via `NEXT_PUBLIC_BACKEND_ORIGIN`.
    95→- **Security model**: credentials (if any) exist ONLY in environment
    96→  variables; no endpoint accepts credentials, terminal paths or anything
    97→  executable; the terminal is never exposed to the public internet; if the
    98→  API is reachable remotely, put it behind your own auth proxy / VPN
    99→  (built-in authentication is a later phase) and restrict the network.
   100→- **Timestamps**: candle times are preserved exactly as MT5 reports them —
   101→  epoch seconds whose wall-clock value is the BROKER SERVER time (the MT5
   102→  convention). Every response also renders the same epoch as ISO-8601 UTC
   103→  (`time_utc`) and carries `timezone: "MT5_SERVER"` with a human-readable
   104→  `timezone_note`. Nothing is ever re-based silently.

   164→## API conventions
   165→
   166→Every response uses the same envelope (`app/core/responses.py`):
   167→
   168→```json
   169→// success
   170→{ "success": true,  "data": { ... }, "error": null,
   171→  "meta": { "request_id": "…", "timestamp": "…", "api_version": "v1" } }
   172→
   173→// error
   174→{ "success": false, "data": null,
   175→  "error": { "code": "RULE_VALIDATION_FAILED", "message": "…", "details": [ { "path": ".conditions[0].operator", "message": "…", "code": "unsupported_operator" } ] },
   176→  "meta": { "request_id": "…" } }
   177→```
   178→
   179→The `request_id` is also returned in the `X-Request-ID` header and appears in
   180→the server's structured logs — quote it when reporting issues.
   181→
   182→### Endpoints
   183→
   184→| Method & path | Purpose |
   185→|---|---|
   186→| `GET /health/live` | Liveness (no dependencies). |
   187→| `GET /health/ready` | Readiness: PostgreSQL probe + market-data status (503 when DB down). |
   188→| `GET /api/v1/meta` | Modes, default timeframes, rule-format whitelists, market-data info. |
   189→| `GET /api/v1/market-data/status` | Honest MT5 availability report (live check). |
   190→| `GET /api/v1/mt5/status` | MT5 terminal/account connection report + safe config summary. **No credentials ever.** |
   191→| `GET /api/v1/market/symbols` | Symbols known to the terminal (`?search=EUR*&limit=100`). |
   192→| `GET /api/v1/market/candles` | Validated OHLCV series (`?symbol=&timeframe=&limit=&closed_only=&refresh=`). |
   193→| `GET /api/v1/market/tick` | Latest tick / bid-ask / spread for one symbol. |
   194→| `GET /api/v1/market/diagnostics` | End-to-end diagnostics: connection + live candle probe + capabilities. |
   195→| `GET/POST /api/v1/strategy-categories` | List (nested, `?mode=&include_archived=`) / create categories & subcategories (`parent_id`). |
   196→| `GET/PATCH/DELETE /api/v1/strategy-categories/{id}` | Manage a category (delete refused while dependents exist). |
   197→| `POST /api/v1/strategy-categories/{id}/archive` \| `/unarchive` | Non-destructive organisation (archive cascades to subcategories). |
   198→| `GET /api/v1/strategies` | Paginated listing (`?mode=&category_id=&status=&include_archived=&page=&page_size=`) → `{items, page:{page,page_size,total,pages}}`. |
   199→| `POST /api/v1/strategies` | Create a strategy (owner-scoped; archived categories refused). |
   200→| `GET/PATCH/DELETE /api/v1/strategies/{id}` | Detail (current rule set + human-readable summary) / update / delete. |
   201→| `POST /api/v1/strategies/{id}/duplicate` | Deep-copy metadata + latest rule set as a new draft (`{name?, include_rule_set?}`). |
   202→| `POST /api/v1/strategies/{id}/archive` \| `/unarchive` | Archive / restore (publish is blocked while archived). |
   203→| `POST /api/v1/strategies/{id}/validate` | Validate a rule set against the schema; the result is persisted (audit trail). |
   204→| `POST /api/v1/strategies/{id}/versions` | Validate + save a NEW immutable **draft** version. |
   205→| `GET /api/v1/strategies/{id}/versions[/{n}]` | Version history (with `status`: draft/published/superseded) / specific version. |
   206→| `POST /api/v1/strategies/{id}/versions/{n}/publish` | Publish a draft version: freezes the definition, supersedes the previous published one, strategy → `active`. |
   207→| `POST /api/v1/rule-sets/validate` | Validate a rule set without saving (editor support). |
   208→| `GET /api/v1/rule-types[/{type}]` | The rule-type registry: parameter schemas, semantics, availability (`available:false` = planned, NOT operational). |
   209→| `POST /api/v1/analysis/evaluate` | Explainable evaluation on user-supplied candles (accepts stored versions or inline rule sets; schema 1.0 and 2.0). |
   210→
   211→**Ownership.** Every strategy/category endpoint is scoped to the requester.
   212→The owner is taken from the optional `X-User-Id` header (1–64 chars,
   213→`[A-Za-z0-9._@-]`; absent/empty → `local`). Requests for another owner's
   214→records return 404, exactly like missing records — no existence oracle.
   215→This is data scoping, not authentication (see Known limitations).
   216→
   217→Structured errors from the market endpoints:
   218→
   219→| HTTP | Code | When |
   220→|---|---|---|
   221→| 422 | `VALIDATION_ERROR` | Bad symbol/timeframe/limit (precise `details[].path`). |
   222→| 404 | `SYMBOL_NOT_FOUND` | Symbol unknown to the terminal. |
   223→| 502 | `MARKET_DATA_ERROR` | Terminal returned an unusable/empty response. |
   224→| 503 | `MARKET_DATA_UNAVAILABLE` | MT5 disabled, package missing or terminal unreachable. |
   225→

   227→

   229→{
   230→  "success": true,
   231→  "data": {
   232→    "symbol": "EURUSD", "timeframe": "M1",
   233→    "timezone": "MT5_SERVER",
   234→    "timezone_note": "Candle timestamps are preserved exactly as reported by MetaTrader 5 …",
   235→    "candles": [
   236→      { "time": 1731608940, "time_utc": "2024-11-14T17:09:00+00:00",
   237→        "open": 1.05651, "high": 1.05662, "low": 1.0564, "close": 1.05655,
   238→        "volume": 812, "forming": false }
   239→      // … newest last; forming candles flagged with "forming": true
   240→    ],
   241→    "count": 3, "requested_count": 3, "closed_only": true, "includes_forming": false,
   242→    "first_time": 1731608940, "last_time": 1731609120,
   243→    "newest_closed_time": 1731609120, "newest_closed_age_seconds": 42.1,
   244→    "data_status": "ok",              // ok | partial | stale | insufficient | empty
   245→    "data_provenance": "mt5_live",    // mt5_live | postgres_cache
   246→    "retrieved_at": "2024-11-14T17:09:37.123+00:00",
   247→    "warnings": [                     // e.g. GAPS_DETECTED, STALE_DATA, INVALID_OHLC…
   248→      { "code": "GAPS_DETECTED", "severity": "warning", "message": "1 gap(s) … NOT back-filled" }
   249→    ]
   250→  },
   251→  "error": null,
   252→  "meta": { "request_id": "…", "timestamp": "…", "api_version": "v1" }
   253→}
   254→```
   255→
   256→**Caching & data distinction.** Raw MT5 responses are validated in-process
   257→(`validation.py`) and — when fresh enough per timeframe — served from the
   258→PostgreSQL `candles` cache (`data_provenance: "postgres_cache"`); otherwise
   259→they are fetched live (`mt5_live`) and persisted. Duplicate inserts are
   260→impossible (composite PK + upsert); the full history is never loaded per
   261→request; a dedicated `refresh=true` request bypasses the cache. No Redis.
   262→
   263→Interactive docs: `http://localhost:8000/docs` (disabled when `APP_ENV=production`).

   265→### The versioned rule format (schema `2.0`, legacy `1.0` supported)
   266→
   267→Full specification: [`docs/strategy-rule-schema.md`](docs/strategy-rule-schema.md)
   268→(+ generated JSON Schema at `docs/strategy-rule-set.schema.json`).
   269→
   270→```jsonc
   271→{
   272→  "schema_version": "2.0",
   273→  "mode": "forex",                          // forex | binary_options
   274→  "timeframes": ["H1", "M15"],              // must be declared here first
   275→  "direction": "bullish",                   // bullish | bearish | both
   276→  "symbols": ["EURUSD"],                    // optional scope (absent = any)
   277→  "market_regime": "trending",              // optional applicability
   278→  "evaluation": { "on_close_only": true },  // optional settings
   279→  "conditions": {                           // root group (required)
   280→    "logic": "AND",                          // AND | OR
   281→    "conditions": [
   282→      { "id": "trend-hold", "type": "moving_average", "timeframe": "H1",
   283→        "lookback": 60, "optional": false,
   284→        "params": { "ma_type": "ema", "period": 20, "compare_to": "value",
   285→                     "value": 1.08, "operator": "above" } }
   286→    ],
   287→    "groups": [ /* nested AND/OR groups (max depth 4) */ ]
   288→  },
   289→  "confirmation": { "logic": "AND", "conditions": [ /* … */ ] },  // optional
   290→  "invalidation": { "logic": "AND", "conditions": [ /* … */ ] },  // optional
   291→  "notes": "free-form user documentation (optional)"
   292→}
   293→```
   294→
   295→**Rule-type registry** (single source of truth: `rule_registry.py`, served at
   296→`/api/v1/rule-types`). Operational in Phase 3: `price_level`,
   297→`candle_property`, `candle_pattern`, `swing_point`, `structure_pattern`
   298→(HH/HL/LH/LL), `market_structure_break`, `moving_average`, `price_zone`.
   299→Planned — documented but **NOT operational**, rejected with
   300→`rule_type_not_available`: `mss_choch`, `liquidity_sweep`, `fvg`,
   301→`order_block`, `breaker_block`, `support_resistance_reaction`. Every
   302→operational type has defined semantics, input validation and tests; a unit
   303→test guarantees registry ↔ evaluator consistency.
   304→
   305→**Legacy 1.0** rule sets (flat `price_level` conditions, direction without
   306→`both`) remain valid and evaluatable — stored strategies from earlier phases
   307→keep working unchanged.
   308→
   309→**Evaluation semantics** (deterministic, documented, tested — see the schema
   310→doc for per-type details):
   311→
   312→- Group `AND` = every **required** child satisfied (unmet *optional* rules
   313→  are reported but never block); `OR` = at least one child satisfied.
   314→- Result status: `conditions_met`, `conditions_missing`, `invalidated`
   315→  (invalidation group satisfied), or `insufficient_data` (referenced
   316→  timeframe has no usable candles — the platform never invents data).
   317→- **No look-ahead bias**: evaluators only use information contained in the
   318→  supplied candles. Swing confirmation requires `strength` subsequent
   319→  candles *inside the data*; a candidate near the right edge never counts.

   323→## Prerequisites

   326→- **Bun** (frontend dev server & tests) or Node 20+
   327→- **Docker + Docker Compose** *or* a reachable PostgreSQL 16

   373→The frontend calls the backend through one of two modes
   374→(`src/lib/api/client.ts`):
   375→

   377→  the same origin with `?XTransformPort=8000` — used by the sandbox preview and
   378→  single-domain deployments.
   379→- **Direct mode**: set `NEXT_PUBLIC_BACKEND_ORIGIN=http://localhost:8000`
   380→  (already the default in `.env.example` for Compose) and add the frontend
   381→  origin to backend `CORS_ORIGINS`.

   383→### Option C — Windows host with a live MT5 terminal (live market data)
   384→
   385→1. Install & start the MetaTrader 5 terminal; log in to your broker.
   386→2. `pip install -r backend/requirements-mt5.txt` in the backend venv.
   387→3. Configure `backend/.env`: `DATABASE_URL` (a reachable PostgreSQL),
   388→   `MT5_ENABLED=true`. Prefer leaving `MT5_LOGIN/PASSWORD/SERVER` empty so the
   389→   backend attaches to the terminal's own login — no credentials stored.
   390→4. `cd backend && alembic upgrade head && uvicorn app.main:app --host 0.0.0.0 --port 8000`
   391→5. Verify: `curl http://localhost:8000/api/v1/mt5/status` →
   392→   `"connected": true`, then open the frontend's **Market** tab.

   508→## Troubleshooting
   509→
   510→| Symptom | Cause & fix |
   511→|---|---|
   512→| Backend exits: `DATABASE_URL …` | Config invalid/missing. Copy `backend/.env.example` → `backend/.env` and set a real PostgreSQL URL. |
   513→| Backend exits: `MT5_LOGIN … MT5_PASSWORD/MT5_SERVER` | Partial MT5 credentials. Provide all three or none (recommended: none — attach to the logged-in terminal). |
   514→| `/health/ready` returns 503, database `down` | PostgreSQL unreachable. `docker compose up -d db`, or let `make backend` provision a local pgserver cluster. The app keeps running and reports honestly. |
   515→| Frontend shows “backend unreachable” | Backend not started. Run `make backend` (or `docker compose up -d backend`). |
   516→| `/api/v1/mt5/status`: package “not installed” | The `MetaTrader5` package is missing or you are on Linux/macOS. Install `backend/requirements-mt5.txt` on the Windows host with the terminal. The API stays honest — no data is faked. |
   517→| `/api/v1/mt5/status`: “Could not connect … after N attempt(s)” | Terminal not running/not logged in. Start & log into MT5, wait ~30s (reconnect cooldown), then press “Check now”. |
   518→| `MARKET_DATA_UNAVAILABLE` (503) with `MT5_ENABLED=false` | Disabled mode (e.g. Docker Compose default). Enable MT5 on a Windows host or run analysis on user-supplied candles. |
   519→| `SYMBOL_NOT_FOUND` | The symbol is unknown to this terminal. Check `GET /api/v1/market/symbols`; some brokers suffix symbols (`EURUSD.i`). |
   520→| `MARKET_DATA_ERROR` “no rate history” | The symbol exists but has no data for that timeframe/history depth. Try another timeframe or a smaller `limit`. |
   521→| Candle response says `STALE_DATA` / `GAPS_DETECTED` | The terminal is serving old or gapped history (market closed, low liquidity, or symbol recently selected). Warnings are informational; nothing is back-filled. |
   522→| Port 8000 already in use | Another backend instance is running — `make backend` detects and skips. Change `API_PORT` if needed. |
   523→| `rule-sets/validate` returns `RULE_VALIDATION_FAILED` | Read `error.details[].path` — each entry pinpoints the exact violation against the whitelist. |
   524→| Rule save rejected: `rule_type_not_available` | The rule set references a PLANNED type (e.g. `fvg`, `mss_choch`). These are documented but not operational. Pick an available type from `GET /api/v1/rule-types`. |
   525→| `strategy_mismatch` on validate | The rule set's mode/direction disagrees with the strategy (a `both` strategy accepts any rule-set direction; a directional one does not). |
   526→| Publish returns `ALREADY_PUBLISHED` / `VERSION_SUPERSEDED` | That version is already the live definition, or a historical one. Save a new draft version instead. |
   527→| Publish returns `STRATEGY_ARCHIVED` | Unarchive the strategy first. |
   528→| `INVALID_OWNER_ID` | The `X-User-Id` header must be 1–64 chars from `[A-Za-z0-9._@-]`. |
   529→| A strategy “disappeared” from the list | It (or its category) is archived. Enable “Show archived”, or `?include_archived=true` / `?status=archived`. |

   531→## Known limitations (Phase 3)
   532→
   533→1. **Ownership is scoping, not authentication** — the `X-User-Id` header
   534→   separates data between users but does not verify identity. Suitable for
   535→   local/single-operator deployments; if the API is reachable beyond
   536→   localhost, front it with your own auth proxy. Built-in authentication
   537→   remains future work.
   538→2. **Real-terminal behaviour is implemented but was NOT exercised** — the
   539→   sandbox cannot run MetaTrader 5. All automated tests use a faithful fake;
   540→   use the documented live procedure above to validate a specific broker
   541→   terminal. Until then, treat live behaviour as unverified.
   542→3. **WebSockets/streaming** are not implemented — the frontend polls every
   543→   15–30 s. Planned next.
   544→4. **Analysis does not consume MT5 candles yet** — `POST
   545→   /api/v1/analysis/evaluate` still evaluates user-supplied candles; wiring
   546→   the evaluator to live `mt5_live` series (explicit provenance label) is the
   547→   next phase.
   548→5. **Planned rule types are intentionally not operational** — `mss_choch`,
   549→   `liquidity_sweep`, `fvg`, `order_block`, `breaker_block`,
   550→   `support_resistance_reaction` are documented in the registry, shown as
   551→   unavailable in the UI and rejected by validation. Their precise
   552→   definitions, edge cases and tests are prerequisite work before activation.
   553→6. **Evaluation settings are declarative** — `evaluation.on_close_only`
   554→   documents intent and is surfaced in summaries; enforcing it end-to-end
   555→   belongs with live-candle evaluation (next phase).
   556→7. **No automatic trading or order execution** — permanently out of scope;
   557→   nothing here sends orders anywhere, and no profitability is claimed or
   558→   implied.
   559→8. The cache serves at most the configured `limit` of latest candles per
   560→   series; deep historical backfill (beyond the terminal's own depth) is not
   561→   attempted.
   562→9. `docker compose` builds the frontend in dev mode; the production build
   563→   path (`Dockerfile.frontend`) was not exercised inside the sandbox.
   564→
   565→## Recommended next step: Phase 4 — live evaluation & backtesting
   566→
   567→1. Wire the evaluator to MT5 candles: evaluate published strategy versions
   568→   against validated `mt5_live` / `postgres_cache` series (explicit
   569→   `data_provenance`), enforcing `evaluation.on_close_only` end-to-end.
   570→2. WebSocket streaming of candle updates + status changes; the frontend
   571→   client already isolates all backend I/O in one module.
   572→3. Historical analysis & backtesting over stored immutable strategy versions;
   573→   the `candles` cache is the natural replay source.
   574→4. Advance the planned rule types (MSS/CHoCH, liquidity sweeps, FVG, order

   577→   frontend changes.
